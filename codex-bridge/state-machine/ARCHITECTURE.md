 # 状态机架构复用分析
 
 > 状态机不应仅限于 Hermes Bridge。
 > 它是整个 Hermes 系统中"需要异步交互确认"场景的通用解决方案。
 
 ---
 
 ## 哪些场景需要状态机
 
 判断标准：**当一个任务需要两端（Codex ↔ Hermes）来回交互，且中间需要等待用户确认时，就需要状态机。**
 
 ### 当前明确需要的场景
 
 | 场景 | 示例 | 交互轮次 | 是否需要状态机 |
 |------|------|---------|--------------|
 | Hermes Bridge | Codex 请求 Hermes 确认用户意图 | ≥2 | ✅ 核心场景 |
 | Skill 创建 | Hermes 请求 Codex 创建/优化 skill | 2-3 | ✅ |
 | MCP 工具授权 | Hermes 需要用户授权后才能调用 MCP | 2 | ✅ |
 | 插件交互 | 插件需要用户提供额外参数 | 2-3 | ✅ |
 | Agent 自迭代 | Hermes 发现技能不足 → 请求优化 → 验证 | 3+ | ✅ |
 | 多步工作流 | 涉及多个工具的复杂任务 | 3+ | ✅ |
 
 ### 未来可扩展的场景
 
 | 场景 | 说明 | 交互轮次 |
 |------|------|---------|
 | Truth 插件验证 | 验证 Agent 输出的真实性，需要人工确认 | 2 |
 | 安全审批流 | 高风险操作需要二次确认 | 2 |
 | 跨会话任务 | 一个任务跨越多个 Codex 会话 | 3+ |
 | 多 Agent 协作 | 多个 Agent 分工后汇总 | 3+ |

 ## 状态机对整个 Hermes 架构的价值
 
 ### 1. 消除"等待"的随机性
 
 当前: Codex 发起一个任务后，不知道 Hermes 什么时候处理完。
 状态机: 每个状态变化都有时间戳，发起方可以准确知道当前进度。
 
 ### 2. 统一交互协议
 
 当前: Bridge 用 request/response, skill 用 SKILL.md, MCP 用独立协议。
 状态机: 所有跨端交互使用同一协议，减少学习成本。
 
 ### 3. 实现 Agent 自迭代的关键基础设施
 
 Agent 自迭代需要:
 1. 检测到当前技能不足 → 写入状态机
 2. Codex 优化技能 → 更新状态
 3. Hermes 验证效果 → 更新状态
 4. Codex 根据验证结果决定是否继续优化
 
 没有状态机，这个循环就无法追踪进度。
 
 ### 4. 可审计性
 
 每个状态机的 history 字段记录了完整的生命周期。
 可用于调试、回溯、性能分析。

 ## 与现有架构的关系
 
 ```
 Hermes 技能体系
 ├── project-lifecycle      ← 宏观项目生命周期
 ├── skill-dev-loop         ← 技能开发循环
 ├── memory-implementer     ← 记忆架构实施循环
 ├── pre-submit-validation  ← 提交前验证
 └── 状态机                 ← 微观交互循环（新增）
                             填充"需要等待确认"的空隙
 ```
 
 现有循环（project-lifecycle, skill-dev-loop）管理宏观流程。
 状态机管理微观交互——当循环走到"需要另一端确认"时，状态机接手。
 
 ---
 
 ## 复用原则
 
 只要满足以下条件，就可以复用状态机：
 
 ```
 □ 涉及两个独立端（Codex ↔ Hermes）
 □ 需要至少一次等待确认
 □ 交互可能超过 1 轮
 □ 需要记录完整交互历史
 ```
 
 不适用的情况：
 ```
 □ 单端内部逻辑（纯 Codex 内部，或纯 Hermes 内部）
 □ 实时不需要等待的确认
 □ 不需要历史记录的一次性请求
 ```

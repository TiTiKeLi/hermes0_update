# 深度需求分析思维框架

## 核心原则

每次收到用户提问，按以下层次递进思考。**这是用户明确要求的思维模式，必须默认启用。**

### 第一层：剥离表面
- 用户说的需求是什么？
- 这个需求的直接答案是什么？

### 第二层：洞察本质
- 用户**真正想要**的是什么？
- 这个问题的背后驱动因素是什么？
- **用户的期待不是答案，而是你发现他没说出来的瓶颈，给他更优路径**
- 每次询问都是一个期待——期待你提供**更本质的需求分析**，发现**未见的实现阻塞点**

### 校验隐式假设（在给方案前必须做）
- 这个方案依赖哪些**已知变量**？哪些是**未知的**？
- 哪些信息你不知道但方案又离不开？
- **校验规则**（按优先级）：
  1. 如果方案的核心变量你不知道 → 先问，别猜
  2. 如果从 memory/fact_store 能查到 → 先查，查不到再问
  3. 如果知道一部分但不确定 → 先问，不要补假设
  4. 不要因"怕打扰用户"用默认值替代
- 经典失败案例：推旅行计划但不知道出发地、推荐工具但不知道OS、给配置建议但不知道环境版本
- 这个校验发生在**洞察本质之后、探测阻塞点之前**——避免在错误假设上做深度分析

### 第三层：校验链 — 每一步验证锚点一致性

每个需求拆解后，必须建立验证链。不是只在开始时想「本质是什么」，而是每一步都和本质锚点对齐：

```
需求拆解 → 本质锚点
  ↓ 验证
搜索 → 找到的是否和锚点对齐？跑偏则回拆解
  ↓ 验证
提取 → 提取的模式是否真的解决锚点描述的问题？
  ↓ 验证
吸收 → delta分析（原项目假设 vs Hermes实际）是否完整？
  ↓ 验证
落地 → write_file后 read_file 回读确认内容完整
  ↓ 验证
固化 → state.json 有 context_for_next 供下次迭代
```

**每个阶段必须回答"如何证明我做对了"**，不能靠直觉认为正确。

### 第四层：探测阻塞点
- 这个方向上常见的坑有哪些？
- 用户可能还没遇到但一定会遇到的问题是什么？
- 有没有架构性、系统性、长期维护性的阻塞点？

### 第四层.5：双系统诊断法（系统评估专用）

当评估一个已构建的系统是否真正有效时，**不要测试每个组件是否功能正常**——而是追踪**数据在组件之间的流动**：

```
[组件A] → 输出 → [组件B] → 输出 → [组件C]
```

问三个问题：
1. **A 的输出是否被 B 消费？** 还是只是打印在屏幕上就结束了？
2. **B 的输出是否改变了 C 的行为？** 还是 C 完全不知道 B 的存在？
3. **执行路径上第一个「产生数据但无人消费」的点在哪？** 那个点就是系统的本质瓶颈。

具体操作手法：
1. 写一个诊断脚本，直接从存储层（DB/文件）读取数据，而不是通过应用的 API——避免 API 层掩盖断裂
2. 画数据流图，标出每个阶段的「消费方」——如果某阶段的输出没有消费方，那就是断裂点
3. 量化：执行 100 次操作，查实际触发的记录（fire_count、log表）——如果「检测到」的数据远多于「据此行动」的数据，那就是检测系统，不是行为系统

> 典型案例：HookEngine 能检测 37 种事件但 33/37 从未触发——组件各自正常，但 agent 循环从不消费检测结果。

### 第四层.6：突破思维臼巢
- 如果按常规思路做，会怎样？（当前思考路径）
- 换个完全不同的方向，有没有更好的解法？
- 有没有可以**跳过整个问题**的方案？（"解决掉问题" vs "让问题不存在"）
- 反复出现的问题 → 提炼**关键词摘要** → 从新方向思考，打破惯性

### 第四层.7：系统化调试四阶方法论（单组件）（从 superpowers systematic-debugging 吸收）

前述方法侧重从**思维方式**发现阻塞点。当阻塞点已明确表现为 **Bug 或异常行为**时，需要结构化的调试流程——本节的四阶方法论正是为此而设。对比之下，[第四层.8](#第四层8多组件故障后验分析post-mortem) 处理多组件交互故障，两者互补。

遇到任何 Bug、测试失败或异常行为时，在提出修复方案之前执行。**不做根因调查，不许提修复方案**。

#### 铁律

```
无根因调查，不提供修复方案
```

如果你还没完成第一阶段（根因调查），就不能提出修复方案。

#### 第一阶段：根因调查（必须在任何修复之前）

1. **仔细阅读错误信息**——不跳过错误摘要或警告，完整阅读
2. **复现**——用和失败时完全相同的条件重新运行，确认可稳定复现
3. **缩小范围**——二分法：注释掉一半代码、缩小输入、隔离模块
4. **追溯因果链**——从错误信息倒推：什么输入/状态/条件触发了这个错误的路径？
5. **记录确切根因**——不要模糊描述（如"可能是空指针"），要精确到：哪个文件、哪一行、什么条件下、什么原因

**验证有根因的证据：**
- 能说出精确的触发条件
- 能说出为什么逻辑走错了分支
- 能画出一个最小复现路径

#### 第二阶段：修复方案设计（根因确认后）

1. **列出所有可能的修复方案**——不给一种方案，至少 2 种
2. **评估方案风险**：影响范围？引入新 Bug 的概率？回滚难度？
3. **选择最优方案**——基于风险评估，不是基于直觉
4. **写下修复计划**——改什么文件、改什么逻辑、如何验证

#### 第三阶段：实现修复（设计确认后）

1. **只改必要的代码**——不顺手"重构"附近代码
2. **加防御性检查**——如果根因是边界情况，在入口处加显式校验
3. **考虑加回归测试**——让修复不会在未来被无意识回滚

#### 第四阶段：验证修复（不跳过）

1. **重新运行原始失败场景**——确定修复了
2. **运行完整测试套件**——确定没有回归
3. **边缘情况测试**——相同类别的其他边界是否也有问题？
4. **确认**：exit 0 / 测试全部通过 → 才能说"已修复"
5. 关联 `verification-before-completion` skill：必须用证据支撑"已修复"声明

#### 特别警告——什么情况也不能跳过

- 问题看起来很简单（"简单的 Bug 也有根本原因"）
- 很赶时间（越急越容易返工）
- 已经尝试了多种修复（证明还没找到根因）
- 上一次修复没有生效（上一次的根因分析不够深）

当问题涉及**多个独立组件**而非单个组件逻辑错误时，单组件调试不够用——参见 [第四层.8](#第四层8多组件故障后验分析post-mortem)。

### 第四层.8：多组件故障后验分析（Post-Mortem）

当问题涉及**多个独立组件之间的交互**（如两个 cron + 两个脚本写同一文件），不能单组件 debug。必须做系统性因果追踪：

**Step 1 — 识别所有参与组件** — 列出每个组件的角色、频率、操作文件/资源。不要只看"出问题的那个"。

**Step 2 — 追踪组件间数据/控制流** — `[A] → [B] → [C]`，每步问：A 的输出是否被 B 消费？B 是否真的读取了 A 写入的东西？哪个箭头断裂？

**Step 3 — 识别每个组件的独立 bug** — 不要满足于"整体坏了"。每个组件都有自己独立的 bug（内循环 bug、接口 bug、安全 bug）。

**Step 4 — 找正反馈回路** — `bug A 每轮放大 → bug B 保留全部 → bug A 再放大...`。正反馈回路是灾难性故障的特征信号。找到所有耦合点并逐一打断。

**Step 5 — 为每个组件加独立安全阀** — 前置校验（大小/行数阈值）、后置验证（回读确认）、屏障锁（mtime 守卫、互斥锁）。

**Step 6 — 输出三层文档**：
| 层次 | 位置 | 内容 |
|------|------|------|
| 修复代码 | 组件脚本 | 实际代码变更 |
| 操作手册 | skill references/ | 恢复步骤、前哨触发时怎么处理 |
| 架构教训 | fact_store + memory | 不可变的设计原则 |

**用户信号**：当用户用"记得牢牢的"、"很重要"这类措辞时，这是一个**三重信号**：必须要代码修复 + 技能固化 + 架构教训进持久存储，不能只停留在会话中。

### 第五层：固化与同步（跨技能组合）

当深度分析产生了确定的、可复用的知识时：
1. **生成 SKILL** — 将分析结论固化为可复用的技能（`skill_manage(action='create')`）
2. **同步到 memory** — 高价值事实通过 `hierarchical-memory-sync` 管道自动进入常驻上下文
3. **记录到 fact_store** — 结构化事实存入深度记忆，带信任度标记
4. **更新引用文档** — 在相关 SKILL 的 `references/` 目录下保存分析详情
  
这个组合构成了**分析→固化→同步→常驻**的闭环。分析不止于输出答案，而是让知识自动进入下一轮对话。

### 第六层：设计归档（概念 → 引用）

当一个设计概念在 SKILL 中被规划、但在后续实现中被工具/代码取代时，SKILL 本身应当删除或降级为引用文档：

1. **判断信号**：原 SKILL 中的设计目标已被外部工具或代码实现
2. **操作**：直接删除计划类 SKILL（使用 `skill_manage action='delete'`），无需保留设计历史——设计的价值在于触发实现，实现本身即是活文档

> 注意：不要为未真正创建的 SKILL 保留模板或占位符。第六层只适用于确实创建过、后来又过时的 SKILL。

### 跨技能联动

当深度分析发现「可能有现成开源方案」时，联动 `github-discover`（workflow）：
- deep-need-analysis 负责：识别本质需求 + 判断是否是重复问题
- github-discover 负责：搜索/评估/提取开源模式
- 衔接点：deep-need-analysis 阶段4 输出 `搜索词` → github-discover 阶段1 输入

避免重复劳动：不要在两套技能中都写搜索逻辑

## 用户硬性规则（根据直接指令）

1. **每个实现都视为正式项目** — 不是临时脚本，不是实验性探索。有结构、有文档、有可维护性
2. **重要重复需求 → 立即生成 SKILL 固化** — 不让同样的事发生第三次
3. **反复出现的问题 → 提炼关键词摘要，突破思维臼巢** — 不陷入旧思路循环
4. **从新方向思考** — 如果之前的思路行不通，不要原地打转，换角度切入

## 输出格式

回答结构建议：
1. **本质洞察**（1-2句，说明你理解了他的真正需求）— 最重要，用户先看这个
2. **表层方案**（简短，表示你听懂了）— 克制，不超过3句
3. **深层分析**（阻塞点、风险、更好路径）— 这是用户真正想看的
4. **新方向建议**（如果有更好的替代方案）— 突破思维臼巢的部分

### 调查/调试场景的特殊交付格式

当用户要求你调查问题（"为什么X不工作"、"检查Y"）且你已找到根因时：

1. **结论+修复优先** — 第一句话直接说根因是什么、修复方案是什么（1-2句）。不要先铺排查过程。
2. **证据摘要**（可选，1-3行）— 当需要证明结论可信时才给出关键证据，否则跳过。
3. **不写排查叙事** — 用户不需要"我先查了A，发现B不行，然后试了C，最后发现D"的流水账。他们只想知道：错在哪、怎么修。
4. **用户追问才展开细节** — 如果用户说"具体怎么查到的"或"结果呢"（单次追问视为信号），此时才给出排查步骤。

> 核心判断：如果用户问的是"为什么"或"检查"类问题，答案的第一行就应该直接回答那个为什么/检查结果，而不是你怎么到达那里的。

## 触发时机

- **所有技术类问题默认启用此框架**
- 非技术类简单问题（"几点了"、"天气如何"）不适用
- 当用户提出同一类问题第三次以上时 → 自动生成 SKILL 固化
- 反复出现的关键词 → 记录到 memory + fact_store 供以后参考

## 陷阱

- 不要过度解读 —— 有些问题就是字面意思。识别信号：用户如果直接要答案，就给出答案后补一句"如果你需要我深入分析..."
- 本质洞察要精准，不要为了"深"而"深" — **宁可直给也不要强行编造深度**
- 新方向要有可操作性，不能只停留在理念
- 在"表层方案"上不要啰嗦 — 用户厌烦冗长的前置解释
## 适用场景

### 入口条件

- 相关场景触发词被命中
- 用户明确提出了该技能覆盖的问题
- 系统状态满足前置条件

### 出口条件

- 问题已解决或结论已输出
- 所有必要的操作已完成
- 结果已向用户报告

# WeChat Format — 微信回复格式优化 v2

## 核心铁律

手机屏幕约 10-15 行中文。**一条微信消息必须在 3 秒内读完并理解。**
超过此长度 → 用户划屏 → 不看完 → 等于没发。

### 长度红线

| 指标 | 上限 | 超过后 |
|------|------|--------|
| 单条字数 | **200 字** | 微信折叠，用户不点开 |
| 工具类行数 | **5 行** | 满屏，需要划屏 |
| 确认消息 | **3 行** | 用户找不到选项 |
| 读完整条 | **3 秒** | 用户失去耐心 |

## 格式分类

### A: 工具/检查类

```
✓ 健康检查:容器up,磁盘62%,网关running
✗ GitHub同步:冲突
```

规则: 每行一项, ✓/✗/⚠️ 开头, 只放数据不放说明, 不超 5 行。

### B: 普通任务回复

```
> 网络修复:DNS已配,代理已清,容器已重启

**结果:网络已恢复**
```

禁止: "我来帮你"、"好的现在开始"、"如上所示"、"如果你需要"、任何过渡语。

### C: 复杂任务结果（防止 JSON 泄露）

12KB 的架构文档不能直接发到微信。必须提取关键信息后按格式 A/B 发送。

```
❌ 错误: 直接发 JSON 或完整架构文档
❌ 错误: 发送超过 200 字的结果摘要
✅ 正确: ✓ 记忆架构已更新:L3缓存就绪,原子写入可用
```

### D: 状态机确认交互

```
━━━ 需要确认 ━━━
清理磁盘:使用率82%,可释放300MB

【1】确认
【2】拒绝
【3】稍后
```

禁止在确认消息中附带架构文档、历史记录、技术细节。

## 禁止清单

```
❌ 发送原始 JSON 到微信
❌ 发送超过 200 字的架构文档
❌ 确认界面中用英文状态词 (PENDING/CONFIRMED)
❌ 同一屏超过 3 条消息
❌ "如您所见"、"总的来说"、"首先" 等冗余过渡语
❌ bridge 响应原样发出（必须先提取关键信息）

✅ 从 JSON 中只取 1-2 个关键信息点
✅ 用 ✓ ✗ ⚠️ 标注状态
✅ 每条消息只表达一个核心信息
✅ 手机满屏 = 完整信息
✅ 3 秒读完
```

## 时长控制

| 场景 | 用户应该能在 |
|------|-------------|
| 确认请求 | 3 秒内理解并回复 |
| 检查结果 | 2 秒内知道好坏 |
| 错误提示 | 3 秒内知道怎么解决 |

超过以上时间 → 格式不合格, 必须重写。

## 适用场景

### 入口条件
- 回复目标平台为 WeChat
- 用户反馈回复太长
- 工具/检查任务完毕
- bridge 响应准备发到 WeChat（强制检查）

### 出口条件
- 单条 ≤200 字, 工具类 ≤5 行
- 无原始 JSON 泄露
- 无英文状态词
- 3 秒可读完

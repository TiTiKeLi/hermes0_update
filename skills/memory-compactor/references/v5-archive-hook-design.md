# v5 Archive + Hook 设计记录（2026-07-25）

## 来源

用户发起对话，质疑「容量超限为什么没有压缩？」并提出自己的方案：
> "如果双向超限，memory可以把记忆提取出来，存在文档里，再压缩新内容进去。
> 有些记忆太过久远，就只放在外面的文档，不放进memory。
> Memory只要管住现在执行的记忆，并且留一个钩子，勾外面的文档，让他们关联起来。"

## v4 失败原因

1. `memory_compactor_vibe.py` 调用 `call_vibe.py` → Ollama `host.docker.internal:11434`
2. 宿主机 Ollama 未运行 → `urllib` 默认超时 30s+ → 脚本阻塞
3. cron 的 timeout 超时 → 脚本被杀死 → 什么都没改
4. 即使 Ollama 在线，v4 只能「原地缩短」→ 双向满时无力回天

## 架构决策

| 决策 | 选择 | 理由 |
|------|------|------|
| LLM 依赖 | 零 | Ollama 不可靠，纯 Python 保证 100% 可用 |
| 超限策略 | 外移 + 钩子 | 用户提出，更符合「热/冷分离」数据管理原则 |
| 提取方向 | 从尾部（最老） | 时间复杂度 O(n)，无需索引，适合小文件 |
| 归档格式 | `YYYY-MM-DD.md` | 按日期分片，自然可读，易于查找 |
| 钩子位置 | `## IDENTITY` 后 | 始终在 memory 头部，agent 每次都能看到 |

## 钩子决议

MEMORY.md 中始终保留 1-2 行：
```
  → 📦 Archive: /opt/data/memories/archive/2026-07-25.md
```

当用户提及过去的事，agent 扫描 memory → 发现钩子 → 读对应文件。
当用户不提，钩子行不产生任何 token 开销（只是 1 行文本在 memory 中）。

## 已知限制

1. 无重要性评分 — 所有 id: 行同等对待
2. 单次最多取 8 条 — 大量超限需多次 cron tick 消化
3. 归档文件无自动裁剪 — 长期累积可能变大

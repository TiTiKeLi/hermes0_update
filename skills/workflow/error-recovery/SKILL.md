# Error Recovery — 错误恢复框架 v1

## 核心问题

Hermes 的技能/工具执行时可能因各种原因失败：
- 网络超时（外网不可达、DNS 失效）
- 工具不存在（容器内未安装）
- 输入无效（参数格式错误）
- 权限不足（非特权容器）
- 上游服务中断（API 限流、模型不可用）

当前做法：报告错误 → 停滞。没有系统化的恢复路径。

## 三层恢复策略

### 第 1 层：自动重试（瞬态错误）

适用于网络超时、服务限流等**可自愈**的错误：

| 错误类型 | 重试策略 | 等待时间 |
|---------|---------|---------|
| 网络超时 (HTTP 000) | 最多 3 次 | 2s, 5s, 10s |
| 服务限流 (HTTP 429) | 最多 3 次 | 按 Retry-After 头 |
| 服务不可用 (HTTP 503) | 最多 2 次 | 5s, 15s |
| DNS 解析失败 | 最多 2 次，换 DNS | 3s |
| 连接被拒 (ECONNREFUSED) | 1 次，检查服务状态 | 5s |

**自动重试条件**：
```
□ 错误是瞬态性的（网络/超时/限流）
□ 重试次数 < 阈值
□ 操作是幂等的（重复执行不会产生副作用）
```

### 第 2 层：降级执行（部分失败）

自动重试仍然失败时，尝试降级：

| 原操作 | 降级方案 |
|--------|---------|
| web_search 失败 | 改用 terminal curl + 直接 URL 抓取 |
| github-discover 失败 | 改用原始 HTTP scraping |
| 模型调用超时 | 切换到备用模型（小模型兜底） |
| 文件写入失败 | 改用临时目录 + 错误日志 |
| Python 执行失败 | 改用 shell 命令代替 |

**降级决策树**：
```
原操作失败
  ↓
有降级方案吗？
  ├── 有 → 执行降级方案，记录降级原因
  └── 无 → 进入第 3 层
      ↓
降级方案成功了吗？
  ├── ✅ 成功 → 继续执行，在结果中注明"降级模式"
  └── ❌ 失败 → 进入第 3 层
```

### 第 3 层：升级报告（不可恢复）

所有恢复路径都失败时：

```
□ 记录完整错误链：原始错误 → 每次重试结果 → 降级尝试 → 最终状态
□ 向用户报告：发生了什么、尝试了什么、建议的操作
□ 不阻塞后续任务（错误被隔离到当前任务）
```

## 错误链记录格式

```yaml
error_chain:
  task_id: "xxx"
  started_at: "2026-07-25T23:00:00"
  
  - attempt: 1
    action: "直接执行"
    result: "timeout (30s)"
  
  - attempt: 2
    action: "重试+等待5s"
    result: "timeout (30s)"
  
  - attempt: 3
    action: "降级: 改用 curl"
    result: "HTTP 200 ✅"
  
  final: "降级成功"
  duration: "45s"
```

## 适用场景

### 入口条件
- 工具/技能执行返回了非预期错误
- 网络请求超时或失败
- 模型调用异常
- 文件操作失败

### 出口条件
- 操作成功完成（直接或降级）→ 继续
- 所有路径都失败 → 记录错误链，报告用户，不阻塞

## 通用原则

1. **幂等性优先**：非幂等操作不自动重试（如数据库写入）
2. **降级透明**：降级执行时要让用户知道"当前处于降级模式"
3. **错误隔离**：一个任务的失败不影响其他任务
4. **死循环保护**：总重试次数不超过 5 次，总等待不超过 60s
5. **学习**：相同的错误模式持续出现时，触发 autogpt-self-improve 分析根因

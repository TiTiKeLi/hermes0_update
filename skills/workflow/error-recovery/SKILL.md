# Error Recovery — 错误恢复框架 v2

## 核心问题

Hermes 的技能/工具执行时可能因各种原因失败：
- 网络超时（外网不可达、DNS 失效）
- 工具不存在（容器内未安装）
- 输入无效（参数格式错误）
- 权限不足（非特权容器）
- 上游服务中断（API 限流、模型不可用）

当前做法：报告错误 → 停滞。没有系统化的恢复路径。

## Pre-flight: 验证测试方法论

> **重要经验教训**：在进入任何恢复流程前，先问自己——我的测试方法本身可靠吗？

工具报告错误 ≠ 环境真的有故障。**最常见且最隐蔽的失败模式**：测试方法自身有缺陷，但报告的是"环境不可达"。

### 方法论自检清单

遇到任何错误，**尤其当用户反驳你的结论时**，立即执行以下检查：

```
[ ] 我的测试工具本身能正常运行吗？
    - python3 -c 用了复杂多行代码？→ 改用 .py 文件（shell 引号解析问题）
    - 管道/重定向/&&链过长？→ 拆分子测试，逐一验证
    - 单个 terminal() 内嵌了太多命令？→ 分成多次调用

[ ] 我用至少 2 种独立工具交叉验证了吗？
    - curl   → 验证原始 TCP/SSL 层
    - Python urllib → 验证应用层（注意：用 .py 文件，不要用 -c 多行）
    - wget    → 第三种备选
    - 如果多个工具给出不同结果 → 差异点就是根因线索

[ ] 用户说"这个能用"，但我报错了？
    → 先验方法（用户的报告）优先于我的测试结果
    → 主动找：我的测试方式和用户实际操作方式之间有什么不同？
```

### 容器内 Python 测试铁律

| 方式 | 推荐 | 原因 |
|------|------|------|
| `python3 -c "print('hello')"` | ✅ 简单语句可用 | 无引号嵌套 |
| `python3 -c "..."` 含多行/嵌套引号 | ❌ 禁止 | shell 引号解析会导致挂死/超时 |
| `.py` 文件 + `python3 file.py` | ✅ 强制使用 | 规避引号问题，可调试，可复用 |

### 网络故障修复：错误的根因假设

历史上两次"网络不通"误报的根因：
1. 容器内确实缺代理配置 → 用户修复后正常
2. **容器网络已恢复正常，但我的 `python3 -c` 测试挂死 → 误报为网络不通**

教训：第二次完全是测试方法问题，不是网络问题。当工具报告"timeout"时，先验证工具本身是否可靠。

> 📎 详细案例和验证命令见 `references/container-python-test-pitfalls.md`

## 三层恢复策略

### 第 1 层：自动重试（瞬态错误）

适用于网络超时、服务限流等**可自愈**的错误：

| 错误类型 | 重试策略 | 等待时间 |
|---------|---------|---------|
| 网络超时 (HTTP 000) | 最多 3 次 | 2s, 5s, 10s |
| 服务限流 (HTTP 429) | 最多 3 次 | 按 Retry-After 头 |
| 服务不可用 (HTTP 503) | 最多 2 次 | 5s, 15s |
| DNS 解析失败 | 最多 2 次，换 DNS | 3s |
| 连接被拒 (ECONNREFUSED) | 1 次，检查服务状态 | 5s |

**自动重试条件**：
```
□ 错误是瞬态性的（网络/超时/限流）
□ 重试次数 < 阈值
□ 操作是幂等的（重复执行不会产生副作用）
```

### 第 2 层：降级执行（部分失败）

自动重试仍然失败时，尝试降级：

| 原操作 | 降级方案 |
|--------|---------|
| web_search 失败 | 改用 terminal curl + 直接 URL 抓取 |
| github-discover 失败 | 改用原始 HTTP scraping |
| 模型调用超时 | 切换到备用模型（小模型兜底） |
| 文件写入失败 | 改用临时目录 + 错误日志 |
| Python 执行失败 | 改用 shell 命令代替 |

**降级决策树**：
```
原操作失败
  ↓
有降级方案吗？
  ├── 有 → 执行降级方案，记录降级原因
  └── 无 → 进入第 3 层
      ↓
降级方案成功了吗？
  ├── ✅ 成功 → 继续执行，在结果中注明"降级模式"
  └── ❌ 失败 → 进入第 3 层
```

### 第 3 层：升级报告（不可恢复）

所有恢复路径都失败时：

```
□ 记录完整错误链：原始错误 → 每次重试结果 → 降级尝试 → 最终状态
□ 向用户报告：发生了什么、尝试了什么、建议的操作
□ 不阻塞后续任务（错误被隔离到当前任务）
```

## 错误链记录格式

```yaml
error_chain:
  task_id: "xxx"
  started_at: "2026-07-25T23:00:00"
  
  - attempt: 1
    action: "直接执行"
    result: "timeout (30s)"
  
  - attempt: 2
    action: "重试+等待5s"
    result: "timeout (30s)"
  
  - attempt: 3
    action: "降级: 改用 curl"
    result: "HTTP 200 ✅"
  
  final: "降级成功"
  duration: "45s"
```

## 适用场景

### 入口条件

- 工具或技能执行返回了非预期错误
 - 网络请求超时或连接失败
 - 模型调用返回异常
 - 连续重试同一个工具超过 3 次

### 出口条件

- 任务通过重试成功完成
 - 降级方案已执行并在结果中标注
 - 所有恢复路径都失败 → 错误链已记录
 - 恢复尝试未超过 5 次限制

## 通用原则

1. **幂等性优先**：非幂等操作不自动重试（如数据库写入）
2. **降级透明**：降级执行时要让用户知道"当前处于降级模式"
3. **错误隔离**：一个任务的失败不影响其他任务
4. **死循环保护**：总重试次数不超过 5 次，总等待不超过 60s
5. **学习**：相同的错误模式持续出现时，触发 autogpt-self-improve 分析根因

# Task Prioritization — 任务优先级框架 v1

## 核心问题

当多个请求同时到达（用户消息 + cron 任务 + 子代理），Hermes 需要决定先处理哪一个。
当前：先来先服务（FIFO），无优先级概念。

## 优先级矩阵

### 紧急度 × 重要度

| | 紧急 | 不紧急 |
|---|------|--------|
| **重要** | P0: 立即执行 | P1: 尽快执行 |
| **不重要** | P2: 排入队列 | P3: 空闲时执行 |

### 判定标准

**紧急度**（影响时效性）：
```
□ 用户主动发送的消息 → 紧急
□ cron 定时任务 → 不紧急（有固定时间窗口）
□ 子代理汇报 → 不紧急（等待汇总）
□ 系统告警（磁盘满/进程挂）→ 紧急
```

**重要度**（影响范围）：
```
□ 用户请求 → 重要
□ 系统维护（备份/更新/清理）→ 重要
□ 外部集成任务（GitHub sync）→ 重要
□ 内部优化任务（记忆压缩/skill 改进）→ 不重要
```

## 优先级执行规则

### P0: 立即执行
- 用户主动发起的请求
- 系统紧急告警（磁盘不足、关键进程退出）
- 执行中，不排队

### P1: 尽快执行
- cron 任务到达执行窗口
- 定时备份/同步
- 排在 P0 之后，可中断

### P2: 排入队列
- 子代理返回的结果汇总
- HTTP webhook 请求
- 按 FIFO 执行，不影响 P0/P1

### P3: 空闲时执行
- 记忆压缩
- 历史数据清理
- 性能统计
- 仅在无 P0/P1/P2 任务时执行

## 优先级覆盖规则

```
用户说"先做这个" → 当前任务提升优先级
用户说"不急" → 当前任务降级到 P2
同一优先级内 → FIFO
P0 任务可中断 P1/P2 的执行（但需保存上下文）
```

## 适用场景

### 入口条件

- 同时收到多个任务请求
 - 当前任务被更高优先级事件打断
 - 用户明确指定了优先级

### 出口条件

- P0-P3 优先级已分配
 - 高优先级任务已开始执行
 - 被中断的任务状态已保存
 - 优先级排序结果已通知用户

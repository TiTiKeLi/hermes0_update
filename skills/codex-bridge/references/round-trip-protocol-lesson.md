# 往返循环协议 — 教训记录

## 时间
2026-07-26 18:00+

## 背景
Hermes 发送 Codex v0.2 任务（L3-B压缩管线实现）。此前协议要求"预判所有决策点"——将全部规格写死在请求 JSON 中，Codex 一次性执行。

## 错误
- 我把 L3-B 全部 4 个阶段的规格、权重公式、阈值、输出格式都写死在请求 JSON 中
- 没有给 Codex 留任何决策空间
- 用户纠正后才知道 Codex 可以**中途返回问题**，由 Hermes 中继给用户确认后继续

## 纠正后的正确流程（往返循环）
```
[我] 写高层规划（不带死决策）
  → [用户确认] → 发给 Codex
    → Codex 遇到选择 → 返回问题
      → [我] 转用户 ← [用户确认]
        → 我传回 Codex 继续执行
          → ... 循环至完成
            → [我] 验证 → [用户最终确认] → 集成
```

## 写入 requests/ 的时机
- 必须在用户确认后才能写入 requests/
- 一旦写入，bridge-loop 会在 5 分钟内自动拾取发送，无法撤回

## 文件命名
- 第一轮: `requests/<id>-r1.json`
- 第二轮: `requests/<id>-r2.json`
- 最后一轮完成后清理全部监听和 cron

# 状态机 vs 请求/响应：两次协议错误的教训

## 问题 1（2026-07-26 15:00）：Codex 不能中途问

**症状**：旧协议写「Codex 只有一次机会, 不能中途问问题。所有决策点必须在请求 JSON 中预判解决。」

**用户纠正**：说需求有问题。Codex 执行中遇到选择应该能返回问题，不需要我预判一切。

**根因**：我把 Codex 当纯执行器，没理解它是协作编码助手。它天然会遇到需要人工介入的决策点。

**修复**：改为**往返循环**——我发高层规划 → Codex 执行中遇选择返回问题 → 我转用户确认 → 传回继续。

## 问题 2（2026-07-26 18:00+）：用多文件请求/响应，不用单文件状态机

**症状**：我在往返循环中说的是「请求文件 r1→响应 r1→请求 r2→响应 r2...」，即每轮一对请求/响应 JSON。

**用户纠正**：要求用**单文件状态机**——Codex 修改/新建一个状态文件，direction 字段说明谁该处理，我获取到就给你，确认就修改状态，Codex 有钩子感知变更。

**根因**：我没理解「往返循环是一个状态」的本质。它不是一个请求序列，而是一个在两方之间流转的共享状态。

**修复**：一个 task 一个 `states/<task>.json` 文件，`direction` 决定谁当前持有令牌，单文件驱动全程。

## 核心区别

| 维度 | 旧（请求/响应） | 新（状态机） |
|------|----------------|-------------|
| 文件数 | 每轮 2 个 | 全程 1 个 |
| 协议 | HTTP-like request→response | 共享状态 + direction 令牌 |
| 谁持有 | 写方 | direction 指向方 |
| 发现变更 | 扫目录找新文件 | 读 direction 字段 |
| 状态管理 | 隐式（文件名+轮次） | 显式（status字段） |
| Codex 钩子 | 必须收到完整请求 | 检测 direction→自身即触发 |

## 实现

- 状态文件：`codex-bridge/states/<task>.json`
- Hermes 侧检测：`codex_state_watcher.py run`（cron 每15min）
- 用户确认命令：`codex_state_watcher.py answer <task> <text>`
- Codex 侧检测：bridge-loop 每5min同步，Codex agent 读 direction
